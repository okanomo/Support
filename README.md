# レビュー指摘事項 整理

## 1. 進め方に関する助言（L218〜223）

**指摘事項**
- 画面をいきなり作る前に、「こういうケースがあるから、この時はこうしたい」というケースを先に洗い出したほうがよい。
- 指摘された一文だけを直すのではなく、それによって前の画面や流れも変わらないかまで見直す。

**対応事項**：ケースの一覧を作り、フロー全体を見直す。

## 2. 共通事項

### 2-1. 誘導員によるタッチパネル操作の前提（L47〜78）

**指摘事項**
- パネルはトラックの運転席の窓の高さにあり、誘導員の手は届かない。脚立を置くのは危ない。
- ハードのリセットスイッチはなく、ブレーカーがあるだけ。
- 誘導員がパネルを操作する案は「多分ない」。

**代替案**
- ハンディ端末からリセット信号を送る。
- ハンディで受付完了と駐車位置の指定をし、続けて引き取りをするか確認して押してもらう。ただ、タイムラグ（どこまで即時に反映されるか）が懸念される。
- 「しばらくお待ちください」の下に、続けて引き取り操作を行うボタンを出す。

**対応事項**：持ち込み後にどうやって引き取りへ続けるかを、ハード側と協議する（物理的な制約があるため協議事項）。

### 2-2. 受付済みシャーシの一覧表示（L186〜217）

**課題**
- 間違えてシャーシを選択し、引き取りをせずに戻した場合など、システム側では「受付取りやめ」か判断できず、「受付中」のまま放置されるデータが生まれる。

**当方案**
- 消さない。受付後にアウトゲートで違うと分かって戻した場合、シャーシは受付中のまま残る。一覧から消すと、センターが消し込みをしない限り二度と出てこなくなる。
- アウトゲートで搬出が完了したものなら、消してもよい。
- ×を押されても、単なる選び間違いなのか受付の取りやめなのか、システムでは判断できない。

**指摘事項**
- 一覧には表示したままで、ハンディの「！」マークのように「受付済み」と分かる表示をつける。
- そうしないと、次に来た人が同じシャーシを選んで現場に行ったが無い、と右往左往する。
- QRを読み込んだ段階で「受付中・引き取り中になっている」と分かれば、「誘導員を呼び出して確認しますか」と案内できる。ドライバーもセンターに聞けて早い。
- ステータスを管理するなら、それを有効に使い、ドライバーの作業時間が減る方向で考える。

**対応事項**：受付済み表示と、その後の問い合わせの導線を含めてフローを見直す（L217で「見直します」と回答済み）。

## 3. インゲート

### 3-1. 【1年目】引き取りで×が規定回数を超えた場合（Dのフロー、L12〜44）

**想定フロー**
- 何度も選んで「違う」となったときのフロー。
- 受付業務時間内は誘導員を呼び出す。
- 時間外は車番を入力してもらい、そのまま持ち出してもらう案。勝手に持ち出されるのは困るが、ドライバーも持ち出せないと困るため、検討中。

**指摘事項**
- 「間違えるケース」をどう定義するかが課題。
- 例えば、表示車番を手入力しても候補に出てこない場合は、記録して出すしかない。
- これは、初年度に巡回作業でも登録されていないシャーシで起こりうる、という認識で合意した。
- この画面にも確認ボタンか誘導員呼び出しボタンをつけるのか、と確認された。

**未決事項**：夜間は呼び出されても困るので、呼び出しボタンを空欄にするか。

**当方案**：4桁を入れて該当しなかった場合、夜間は「車番4桁を入れて持ち出しました」の画面へ移るボタンにする。

**対応事項**
- フローを勤務時間中と勤務時間外の2パターンで書き分ける。
- どこで分岐させるかを整理する。

### 3-2. タグ読み取りで×を2回押した場合・受付時間外のフロー（L115〜142）

**想定フロー**
- 受付業務時間内は誘導員を呼び出す。
- 時間外は誰もいないので、とりあえずC・Dに止めてもらう。ただし表示シャーシ番は入力してもらう。

**確認内容**：表示シャーシ番は下4桁だけでよいか。

**指摘事項**
- 初年度は、下4桁ではヒットしないシャーシがあることを必ず考慮する。
- 検索はせず、入力して確認を押したら、その値をそのまま保持する形でよい。
- ヤードマップへの登録方法を決める必要がある。
- 下4桁しかないシャーシは、マスタ未登録のシャーシとして扱い、巡回作業員に正式な値を登録してもらう。
- シャーシマスタへの登録（仮登録）は、一旦しておいてもよい（陸運コードなどが一切ないものが1件登録される形）。そうしないとヤードマップでの表示が煩雑になる。

**要確認事項**
- 巡回作業員がハンディでフルのシャーシ番を入れたとき、正しく上書き登録されるか。現状の作りでは「行方不明」扱いになる可能性がある。
- そもそも「行方不明」の扱い自体が定まっていない（作りたいと言っていた人が、今は作りたくないと言っている）。

### 3-3. 【2年目】持ち込みで×が規定回数に達した場合と呼び出し通知（L61〜73）

- フローは1年目と同じ。
- **Nさんコメント**：呼び出しボタンを押すとハンディに通知が飛ぶようにしたほうがよい。
- **当方案**：ボタンを押さなくても、この画面に来た時点で誘導員に通知が飛ぶほうがよい。

**指摘事項**
- Nさんは、受付と誘導員を混同しているのではないかと思われる箇所がある（実際に、そう読める書き方のコメントが何箇所かある）。
- このコメントは無視してよい。

**対応方針**：画面に来た時点で自動で通知する方針で進める。

### 3-4. 【2年目】引き取り（L74〜108）

**「駐車位置が分からない場合」の分岐に関する指摘事項**
- 下船時にタブレットで駐車位置を登録しているので、ほぼありえないはず。
- どういうケースで起きるのか、当方・レビュアーとも把握できていない。
- 整理して、この分岐が要るかどうかを判断する。
- ヤード管理から駐車位置を返せなかった場合、API連携でどんな値を返すかを決める。
- 発生時の流れ：「どこにあるか分からないので探してください」と表示する。見つけたら連結して、アウトゲートへ来る。
- ×が規定回数以上の場合は変更なし。

**対応事項**
- 駐車位置が不明になるケースを整理し、分岐の要否を決める。
- API連携で返す値を決める。
- 2年目に追加機能が必要か検討する。

**要確認事項：オレンジの未着エリアを本船ごとに分けるか、本船＋向け先で分けるか**
- 現状の想定は本船ごとのみで、向け先までは考慮していない。
- Gさんのタブレットも向け先は考慮していない。
- → 要件をヒアリングして確認する。

## 4. アウトゲート

### 4-1. 【1年目】（L140〜201）

**処理フロー**
- 待機画面でシャーシの到着を検知したら、読み取りに切り替わる。
- 読み取れたら確認画面へ。読み取れなければ、QRか手入力で車番を特定してもらう。
- ○の場合：1年目は判別がつかないので、そのまま搬出。
- ×の場合：
  - 勤務時間内は呼び出し。
  - 時間外は、どのシャーシが出たかだけ入力してもらって搬出。対応を検討中。

**指摘事項（夜間・チェック条件）**
- 夜間は結局「そのままお進みください」と出すしかない。
- 初年度に「そのままお進みください」を出す条件を、MSRの中で決めておく必要がある。
- インゲートで受付済みのシャーシと、アウトゲートに来たシャーシが一致するかチェックするのか。
  - 以前「搬出許可」と記載していたのは、このチェックを意図したもの。
  - 経緯：Sさんから「インゲートを通らずに来たらどうするのか」と質問があり、エラーにすると回答している。

**検討事項**
- 例外パターンでも登録させて出すか。
- 弾く場合は、候補に出さないのか、選んだ後に「受付されておりません」に遷移させるのか。

**指摘事項（エラーの出し方）**
- フローは変えずに確認画面まで出し、○を押した後の結果表示でエラーにする。
- ソフト開発側としても、変更は結果表示のみにとどめたい。

**夜間の扱い**
- インゲートで4桁を入力して登録されているはずなので、その中から出して遷移させる。
- 整合の取りようがないので、「持ち出されました」という履歴を残すのみとなる。

**指摘事項（その他）**
- そもそもゲートを通らずに持ち出され、巡回で初めて判明するシャーシも多いはず。
- 引き取りのチェックをどうするかは、MSRの中で検討する。

**対応事項**
- 現状チェックなしになっているフローを修正し、受付済みかのチェックを入れる（L201で回答済み）。
- MSRの中で、引き取りチェックと夜間の扱いを検討する。

### 4-2. 【2年目・勤務時間内】（L202〜278）

**想定フロー（3パターン）**
1. ○を押し、引き取り可能なら、そのまま進む。
2. 引き取りできない場合（受付されていないタグなしシャーシなど）は、車番を再入力してもらう。
3. ×を数回押した場合、またはタグを読み取ったうえで×の場合は、誘導員を呼ぶ。

**指摘事項**
- 「受付されていないタグなしシャーシ」に限らない。タグの有無に関係なく、受付されていないシャーシ全般がこのケースに該当する。
- 受付されていないシャーシは、再入力とは関係ない。素直に「受付されていません」と出せばよい。

**対応方針**
- 条件を「×ボタン1回」または「規定回数以下」と書き直す。
- 受付されていないシャーシ用の画面を追加する。

**文言**
- 指摘事項：「シャーシ番号を確認し、再度入力してください」程度でよいのでは。
- 懸念事項：正しいと思って入力した人には意味が伝わらないのでは。
- 決定事項：×を押しているので問題なし。

**受付されていないシャーシの扱い**
- 当方案：「ちゃんと受付してください」とアナウンスする。
- 指摘事項：受付されていないシャーシは、誘導員を呼び出してよい。
- 補足：誘導員が口頭で「インゲートに行ってください」と伝えるか、ドライバーが持っているQRを読み込ませれば済む。
- 指摘事項：画面は「インゲートで受付されていません」でよい。
- Nさんの「インゲート受付と違う場合は」という記載の意図：受付されていない場合はこちらのフローへ、ということ。入力が間違っていなくても、インゲートで受付していなければメッセージを出し、誘導員を呼んで確認したい、という意味。

**懸念事項**
- アウトゲートは現状1つのみ（インゲートからヤード1個分ほど隣）。
- ドライバーを待たせると、後ろに次の搬出車両が並んで渋滞にならないか。
- 現地に待機エリアはない。
- アウトゲートにどれだけ滞留するかは予想できないと言われている（下船シャーシが降りるタイミングで詰まるのは明らかであるにもかかわらず）。
- 決定事項：予測できない以上、呼び出す形とする。

**対応事項**
- 勤務時間内はこのフローで進める。
- 受付されていないシャーシは、「インゲートで受付されていません」と表示して誘導員を呼び出す形にする。
- 「受付されていないシャーシ」用の画面を追加する。
- 条件の記載を修正する。

### 4-3. 【2年目】タグ読み取りで×を押した場合（L279〜323）

**レビュアー確認事項**：タグを読み取って○を押し、シャーシは合っていたが受付されていなかった場合に誘導員へ回すのか。タグ読み取りなら、受付されていないケースがすべてそちらに落ちるのでは。

**検討経過**
- インゲートで引き取りの受付をしたのに、タグで全く違うシャーシが出た場合、ドライバーは×を押す。
- Nさんは「タグの読み取りで間違えることはない」という前提で、1回目の×で呼び出しにしたい。
- インゲートもすでにそのように変更済み（タグ読み取りで×なら、再入力ではなく1回目で呼び出し）。

**懸念事項**
- 貼り付けたタグ自体が間違っているケースは必ずある。
- それを検出できるのはゲートのみ。
- ただし、タグの登録に自信を持っている側がそう判断するなら、それに従う。

**決定事項**：タグ読み取りで×の場合の「1回目で呼び出し」は残す。

### 4-4. 【2年目・勤務時間外】×入力時のメッセージ（検討・修正）

**対象**：アウトゲート2年目の勤務時間外で、ドライバーが「×（違う）」を押した場合の画面遷移

- **タグ読み取りの場合**：タグが正しい前提に立つと、ドライバーが引っ張ってきたシャーシ自体が間違っている可能性が高いため、「引き取り対象のシャーシが間違っている可能性があります」と確認を促すメッセージを出す。
- **手入力で×を繰り返す場合**：「シャーシを確認して再入力してください」といったメッセージを出し、再入力を求める（実質的なループ）。ドライバーが無視して退出した場合でも、2Dセンサーで車両の退出を検知すれば画面はリセットされるため、システム上の無限ループは回避できる想定とする。
